## Database

The initial platform schema lives in [`db/schema.sql`](db/schema.sql) and targets PostgreSQL 15+.
It establishes organization-scoped access, farm and field management, crop cycles, sensor telemetry,
field operations, inventory tracking, and marketplace listings.

Apply it to a PostgreSQL database with:

```bash
psql "$DATABASE_URL" -f db/schema.sql
```

The main relationships are:

- An organization has members, farms, inventory, tasks, and marketplace listings.
- A farm contains fields; fields contain crop cycles and sensors.
- Sensors produce timestamped readings, while crop cycles provide harvest context.
- Inventory movements record changes to inventory items instead of mutating history.
- Buyers place offers against listings; an offer belongs to the buying organization,
  and records which of its members placed it.

#### Offers

`offers` (migration `003`) is keyed to the listing and to the *buying organization*
rather than to a person. The whole buying side needs to see and act on a bid, and every
authorization check in the API resolves an owning organization, so an offer owned only
by a user would sit outside the tenancy model entirely. `buyer_id` records which member
placed it and is set to NULL if they leave, matching `tasks.assigned_to` and
`inventory_movements.recorded_by` — the offer outlives the person.

`price_per_unit` and `quantity` carry the precision and scale of the listing columns
they are bid against (`NUMERIC(12, 2)` and `NUMERIC(14, 2)`, in kilograms), so an offer
can be compared with the asking price without rounding. Zero is allowed on price — a
giveaway — but not on quantity.

Deleting a listing or a buying organization cascades its offers away. A partial unique
index allows only one `pending` offer per buyer per listing, so improving a bid replaces
the standing one, while a buyer whose offer was rejected is free to make a new one.

Status values are lowercase (`pending`, `accepted`, `rejected`) to match the ten enums
already in the schema, which is also what the generated client and the Zod schemas
expect.

### Application layers

`prisma/schema.prisma` mirrors `db/schema.sql`, keeping snake_case column and table
names via `@map`/`@@map` so it matches an existing database. Run `npm run db:generate`
(also wired to `postinstall`) to produce the client in `app/generated/prisma`.

- `lib/types.ts` — row types and enums re-exported from the generated client, plus
  relation-loaded shapes and `Serialized<T>` DTOs for values crossing the Server →
  Client Component boundary (`Date`, `Decimal`, and `BigInt` do not survive it).
- `lib/validations/` — Zod schemas for create/update/query payloads.
- `lib/serialize.ts` — converts rows to those DTOs. Decimals become exact strings
  rather than numbers, since a `NUMERIC(14, 5)` value can outrun a JS double.
- `lib/api.ts` — response envelope, validation and infrastructure error mapping,
  route-parameter parsing, and pagination metadata shared by every handler.
- `lib/auth/` — password hashing (`password.ts`), server-side sessions
  (`session.ts`), and the route guards that consume them (`guards.ts`).

Prisma cannot express `CHECK` constraints, partial unique indexes, or the
`set_updated_at()` triggers, so `db/schema.sql` remains authoritative for those. They
are mirrored in the Zod schemas, and anything generated by `npm run db:migrate` must
have them re-applied by hand.

Everything Prisma *can* express is kept exactly in step with the database, so that

```bash
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
```

reports an empty migration. That makes the command a drift detector: any output is a
real difference between the schema and the database, worth reading. Two conventions
keep it quiet, and both need to be followed by anything added later:

- **`onUpdate: NoAction` on every relation.** Prisma assumes `ON UPDATE CASCADE`, while
  the DDL leaves SQL's default of `NO ACTION`. Nothing depends on the difference —
  primary keys are generated UUIDs and are never updated — but without it all 23
  foreign keys report as changed and the real differences are lost in the noise.
- **`@default(now())` alongside `@updatedAt`.** `@updatedAt` on its own tells Prisma
  the column has no database default, but all five timestamped tables declare
  `DEFAULT now()`. Both together match the column as it actually exists: the default
  fills it on insert, and `set_updated_at()` maintains it thereafter.

## HTTP API

Every route lives under `app/api/`, runs on the Node runtime, and answers with the
`ActionResult` envelope from `lib/types.ts` — `{ ok: true, data }` or
`{ ok: false, error, fieldErrors? }`. List endpoints add `pagination`
(`limit`, `offset`, `total`, `hasMore`) and accept `?limit=&offset=`.

| Resource | Endpoints |
| --- | --- |
| Health | `GET /api/health` |
| Auth | `POST /api/auth/register` · `POST /api/auth/login` · `POST /api/auth/logout` · `GET /api/auth/session` · `POST /api/auth/password` |
| Organizations | `GET POST /api/organizations` · `GET PATCH DELETE /api/organizations/:id` |
| Members | `GET PUT DELETE /api/organizations/:id/members` |
| Users | `GET POST /api/users` · `GET PATCH DELETE /api/users/:id` |
| Farms | `GET POST /api/farms` · `GET PATCH DELETE /api/farms/:id` |
| Fields | `GET POST /api/fields` · `GET PATCH DELETE /api/fields/:id` |
| Crops | `GET POST /api/crops` · `GET PATCH DELETE /api/crops/:id` |
| Crop cycles | `GET POST /api/crop-cycles` · `GET PATCH DELETE /api/crop-cycles/:id` · `POST /api/crop-cycles/:id/harvest` |
| Sensors | `GET POST /api/sensors` · `GET PATCH DELETE /api/sensors/:id` |
| Readings | `GET POST /api/sensor-readings` |
| Tasks | `GET POST /api/tasks` · `GET PATCH DELETE /api/tasks/:id` |
| Inventory | `GET POST /api/inventory` · `GET PATCH DELETE /api/inventory/:id` · `GET POST /api/inventory/:id/movements` |
| Listings | `GET POST /api/listings` · `GET PATCH DELETE /api/listings/:id` |
| Offers | `GET POST /api/offers` · `PATCH /api/offers/:id` |
| Admin | `GET /api/admin/organizations` · `PATCH /api/admin/organizations/:id` |

Status codes are consistent across resources: `400` for a malformed body or query,
`401` when a session is required and absent, `403` when the caller is signed in but
lacks the role, `404` for a missing (or non-UUID) id, `409` for a unique or
business-rule conflict, `422` for a foreign key that points at nothing, `503` when
the database is unreachable, and `500` for anything else — logged in full, opaque in
the response.

### Behaviour worth knowing

- **Harvest** — `POST /api/crop-cycles/:id/harvest` takes `actualYield` with a `unit`
  (`kg`, `g`, `t`, `quintal`, `lb`, and their common spellings) and converts to
  kilograms before storing, because `actual_yield_kg` is kilograms by definition. It
  sets the date, yield, and status together and validates the harvest date against the
  planting date already on the row.
- **Reading ingest** — `POST /api/sensor-readings` takes up to 1000 samples and skips
  duplicates on `(sensor_id, recorded_at)`, so a gateway retrying after a timeout can
  re-send its whole buffer. The response reports `received`, `inserted`, and `skipped`.
- **Stock movements** — `POST /api/inventory/:id/movements` writes the movement and
  moves the item's balance in one transaction. `direction` (`in`/`out`) is implied for
  `purchase` and `usage` and required for `adjustment` and `transfer`. A withdrawal
  larger than the balance is refused with a `409` rather than driving the column
  negative, and the check and the decrement are a single statement so concurrent
  withdrawals cannot both succeed against the same balance.
- **Task completion** — moving a task to `done` stamps `completed_at`, and moving it
  off `done` clears it, matching `CHECK (completed_at IS NULL OR status = 'done')`.
- **Deleting an organization** — the tenant's crop cycles and crops are removed
  explicitly before the organization row. `crops` cascades from the organization but
  `crop_cycles.crop_id` is `ON DELETE RESTRICT`, and Postgres does not order a cascade
  so that the cycles go first.

## Authentication

Sessions are server-side. Signing in mints a 256-bit random token, returns it in an
httpOnly `agritech_session` cookie, and stores only its SHA-256 in `sessions` — so a
leaked database dump cannot be replayed as a live session, and any session can be
revoked. Passwords are hashed with scrypt from `node:crypto` (N=2^15, r=8, p=1), which
keeps the platform free of a native build dependency; the cost parameters are stored
in each hash, so raising them later re-hashes on next sign-in instead of invalidating
anyone.

- `POST /api/auth/register` — creates the account, signs it in, and optionally creates
  an organization in the same transaction with the new user as its `owner`. Slug
  collisions take a short random suffix rather than failing the sign-up.
- `POST /api/auth/login` — a wrong password and an unknown address return the same
  `401` and do the same work: `verifyPassword` runs a full scrypt derivation against a
  dummy hash when there is no account, and memberships are only loaded after the
  password verifies, so neither branch is measurably faster than the other.
- `POST /api/auth/password` — requires the current password, and by default revokes
  every other session, re-issuing the caller's own so they stay signed in on the
  device they changed it from.
- `GET /api/auth/session` — the current user plus their role in each organization.

`users.password_hash` is excluded from every query by the client-wide `omit` in
`lib/prisma.ts`, so it cannot reach a response through a relation include or a
whole-row serialization. Sign-in is the one place that asks for it back explicitly.

## Pages

The app is a thin shell over the API: two signed-out pages, and everything else
behind a session.

| Route | Purpose |
| --- | --- |
| `/signup` | Create an account, optionally creating an organization you own. |
| `/login` | Sign in. |
| `/` | Dashboard: the selected organization's crops and listings. |
| `/crops/new` | Add a crop to the selected organization. |
| `/listings/new` | List produce for sale. |
| `/marketplace` | Every published listing, cheapest first. |
| `/marketplace/:id` | One listing — bids if you are selling, a bid form if you are not. |
| `/organizations/new` | Create an organization; you become its owner. |
| `/admin` | Platform administrators only: the verification queue. |

### Dashboard

`/` shows one organization at a time. Which one is decided from the session — a
`?org=` that names an organization the caller does not belong to is ignored and the
first membership is used, so a stale link degrades to a working page instead of a 403.
Someone in more than one organization gets a switcher; someone in one gets no
redundant chrome. Listing cards carry their status transitions (publish, mark sold,
archive), each a `PATCH { status }` on the listing.

Server Components reach the data by calling the API over HTTP with the session cookie
forwarded (`lib/server-api.ts`) rather than querying Prisma directly. Every scoping
rule already lives in the route handlers and is tested there; going through HTTP reuses
those rules exactly instead of reimplementing them beside the markup, where the two
would drift.

The cost is a local round trip per panel, and it is not free: against a remote database
in development the dashboard renders in roughly 1.8s, since each call re-resolves the
session before running its query. Two things already cut it — `getCurrentSession` is
memoized per request with React's `cache`, and the page decides which organization to
show from the session so all three requests go out in parallel rather than in series.
If it needs to be faster still, the fix is to extract the queries into functions that
the routes and the pages both call — not to hand-roll the scoping again in a page.

Each panel renders its own error, so one failing request degrades that section rather
than blanking the dashboard.

Route groups do the gating. `app/(auth)/layout.tsx` redirects anyone who is *already*
signed in to `/`, and `app/(app)/layout.tsx` redirects anyone who is *not* to `/login`
and renders the header with the signed-in email and a sign-out button. Splitting them
this way means neither layout can bounce a request into the other forever, which a
single check at the root would.

That redirect is what makes the pages private in the browser; it is not what makes the
data private. Every API route still runs its own `requireUser()` and membership checks,
so a request that skips the UI is refused regardless.

### Organizations

Anyone signed in may create an organization at `/organizations/new` and becomes its
owner. Until this existed, someone who signed up without naming an organization landed
on a dashboard telling them to create one with nothing to click — `POST
/api/organizations` had always allowed it, but nothing in the app asked.

Two tenants may legitimately share a display name, so a derived slug that collides
takes a short random suffix (`green-valley-farms-7f3a`) instead of failing a request
whose slug the caller never saw. A slug sent explicitly is taken at the caller's word
and a collision is theirs to resolve. Registration and this endpoint share one
implementation of that rule (`availableSlug` in `lib/slug.ts`).

### Marketplace and bidding

`/marketplace/:id` is one page that shows two different things depending on who is
looking: the selling organization's members see every bid with accept and reject
buttons, and everybody else sees a bid form and their own bids. The page does not
implement that rule — it renders whatever `GET /api/offers?listingId=` returns, and the
API is what decides that a buyer sees only their own bids. A UI branch and a security
boundary in the same place would eventually disagree; this way the page can only ever
show what the caller was already allowed to fetch.

The bid form starts at the seller's asking price and quantity, since agreeing outright
is the common case and retyping the numbers to do it is friction. While a bid is
awaiting an answer the form is replaced by its status, because a second pending bid on
the same listing is refused by the database; once the seller answers, the form returns.

`GET /api/listings` now includes the seller's name, so a marketplace row can say who is
selling without a query per row.

### Forms

Forms post to the API routes and render the `ActionResult` envelope through the shared
components in `components/form.tsx`:

- `Field` wires a label, an optional hint, and any `fieldErrors` for that input to the
  control, including the `aria-invalid` and `aria-describedby` a screen reader needs —
  an error nobody is told about is not handled.
- `FormError` shows failures belonging to no single input, such as a wrong password.
  It is suppressed when individual fields are already marked, so a generic
  "Validation failed." never sits above three specific messages.
- `lib/forms.ts` posts JSON and always returns the envelope, turning a dropped
  connection or a non-JSON response into a message the form can show rather than an
  unhandled rejection.

Submission is handled with `onSubmit` and `preventDefault` rather than `<form action>`:
React resets an uncontrolled form once an action resolves, which would empty every
field the moment one of them failed validation — leaving someone who mistyped a
password to retype their name, email, and organization too.

Nested payload errors are flattened onto their top-level key by Zod, so a problem
inside the `organization` object arrives as `organization` rather than
`organization.name`; the sign-up form shows both keys on the organization name field.

## Authorization

Every endpoint except `register`, `login`, `logout`, and `health` requires a session.
`organizationId` is never trusted from a request: it is either resolved from the
caller's memberships or checked against them.

### Roles

`lib/auth/guards.ts` states the policy once, as four tiers, so route handlers name a
tier instead of a role:

| Tier | Role | Covers |
| --- | --- | --- |
| `READ` | `viewer` | Reading anything the organization owns. |
| `WRITE` | `operator` | Day-to-day records: tasks, crop cycles, readings, stock movements, and creating farms, fields, and sensors. |
| `MANAGE` | `manager` | Deletes that cascade — farms, fields, sensors, crops, inventory items, listings. |
| `ADMIN` | `owner` | The organization itself: renaming it, changing the roster, deleting the tenant. |

The brief asked for `owner` and `member`; the schema already had four roles, so these
are the four, with `member` split into the read/write/manage tiers above.

### How a request is scoped

- **Resources with an `organization_id`** (farms, crops, tasks, inventory, listings)
  authorize against it directly.
- **Resources without one** (fields, crop cycles, sensors, movements) resolve their
  owning tenant by walking up the hierarchy — `lib/auth/scope.ts` does this in a single
  narrow query per check. A resource in another tenant is `403`; one that does not
  exist is `404`.
- **Writes** take the tenant from the session. `organizationId` may still be sent,
  because a user can belong to several organizations and the session alone cannot say
  which one a new farm goes in — but it can only ever select among the caller's own,
  never target somebody else's. A caller in exactly one organization may omit it; one
  in several must name it, or the request is a `400`.
- **List endpoints** are scoped to the caller's memberships rather than filtered by a
  query parameter. Naming another tenant's `organizationId` is a `403`, not an empty
  page, so a permissions problem never looks like missing data.
- **Nested ids in a payload** are each authorized separately. A task naming a farm, a
  listing naming a crop cycle, a field naming a farm — each is checked, so a write
  cannot be used to attach the caller's records to another tenant's land.
- **People named in a payload** — a task's `assignedTo`, a movement's `recordedBy` —
  must share the organization, which is also why `recordedBy` defaults to the caller.

### Offers: one resource, two owners

Offers are the first resource that does not have a single owning organization. A bid
sits between the buyer who made it and the seller who owns the listing, so
`requireResourceRole` — which resolves one owner — cannot express the rules.
`findOfferParties` returns both sides instead, and each endpoint decides:

- **Placing a bid** (`POST /api/offers`) is `WRITE` in the *buying* organization. The
  seller is never taken from the payload; it is whoever owns the listing. Bidding on
  your own listing is refused, and a listing that does not exist, is still a draft, or
  is already sold all give the same answer — so the endpoint cannot be used to discover
  which listing ids are real, or to watch another tenant's drafts.
- **Reading** (`GET /api/offers`) serves both sides from one endpoint, because who you
  are decides what you see: a member of the *selling* organization sees every bid on
  its listings, while everyone else sees only the bids their own organizations have
  made. That distinction is the point — without it, `?listingId=` would let one buyer
  read every rival bid on a listing. Highest price first, the order a seller decides in.
- **Answering** (`PATCH /api/offers/:id`) is `WRITE` in the *selling* organization. A
  buyer can read their own offer but gets a 403 explaining that only the seller may
  answer it. The transition is guarded so an offer leaves `pending` exactly once: two
  managers answering at the same moment cannot both succeed, and a rejection cannot be
  quietly reversed.

Accepting a bid deliberately does not mark the listing sold or turn down the others. An
offer may be for part of the listed quantity, so what happens to the remainder is the
seller's decision, made through `PATCH /api/listings/:id`. A buyer whose bid was
rejected may bid again; the partial unique index only stops a second *pending* bid.

**Withdrawal** (`PATCH { status: "withdrawn" }`) is the buyer's counterpart, authorized
against the organization that *made* the bid. A seller cannot withdraw on a buyer's
behalf — refusing is what `rejected` is for, and the two need to stay distinguishable
afterwards, which is why `withdrawn` is a fourth status rather than a reuse of the
third. Withdrawing is as final as any other transition, but it does free the buyer to
bid again: the index that allows one live bid per listing counts only `pending` ones.
The seller keeps seeing the withdrawn bid, labelled as taken back.

### Platform administration and verification

Every privilege in `organization_members` describes authority inside one organization,
so none of them can express "may review other people's tenants". Verification therefore
needs a privilege that is not scoped to a tenant at all: `users.is_platform_admin`,
checked by `requirePlatformAdmin()`.

**That flag must never enter `updateUserSchema`.** Users can already PATCH their own
record; the moment the flag is accepted there, platform administration becomes
self-service. The schema takes email, full name, and phone, and that is the whole
reason it should stay that way. The first administrator is promoted by hand:

```sql
UPDATE users SET is_platform_admin = true WHERE email = 'you@example.com';
```

The flag is read into the session, so an existing session must be signed out and back in
before it takes effect.

`organizations.verified_at` is NULL until granted — a timestamp rather than a boolean,
so the row records *when*, and revoking is setting it back to NULL through the same
endpoint. The admin routes live under `/api/admin` rather than beside the tenant-scoped
ones precisely because they break the rule those follow: they see every organization,
and putting them in the same folder would make the exception easy to imitate by
accident. `PATCH /api/admin/organizations/:id` can change nothing but `verified_at` —
a route able to edit any tenant's name or type would be a far larger hole than the one
it exists to fill.

**Verification gates selling, not membership.** An unverified organization can do
everything else — farms, fields, crops, cycles, sensors, tasks, stock — but
`POST /api/listings` refuses it with a 403, and its listings stay off the marketplace.
The dashboard says so plainly and hides the "New listing" link, rather than letting
someone fill in a form that can only be rejected.

A listing is visible when **either** it belongs to one of the caller's own
organizations — all of their own rows, whatever the status, verified or not, because
this endpoint also backs their dashboard — **or** it is published by a verified
organization, which is what puts it on the public market. The same rule guards
`GET /api/listings/:id`, so a direct link cannot walk past the marketplace filter, and
`POST /api/offers`, since verification can be revoked after a listing was published.

Revocation is therefore immediate and non-destructive: buyers stop seeing the listing
and can no longer bid, while the seller keeps it on their own dashboard.

`/admin` answers as a missing page for anyone without the flag rather than 403 — a
permission error would itself disclose that platform administration exists.

### Two deliberate exceptions

- **The marketplace crosses tenants on purpose.** `GET /api/listings` returns every
  `active` listing on the platform to any signed-in caller — a marketplace where you
  can only see your own produce would be pointless — plus all of the caller's own
  listings whatever their status, so drafts, sold, and archived rows stay private to
  the seller. Editing one is still `WRITE` in the owning organization.
- **`GET /api/health` stays reachable without a session,** because an uptime probe
  cannot sign in. It reveals only that the service and database are up; the row counts
  are returned only to a signed-in caller, and only for that caller's own tenants.

### Still open

- **`POST /api/sensor-readings` needs device credentials.** It is called by field
  gateways, not people, and a gateway cannot hold a browser cookie. It currently
  requires a session with write access to every sensor in the batch — correct, but not
  usable by real hardware. The fix is a per-device token issued when a sensor is
  registered, presented as a bearer header, scoped to that device's sensors, and
  revocable when the hardware is lost. Marked `TODO(device credentials)` in the route.
- Platform-wide crops (`organization_id IS NULL`) are readable by everyone and
  writable by nobody through the API, since there is no platform-administrator role to
  hold that privilege.
- No rate limiting on `/api/auth/login` (a per-address and per-IP limit belongs in
  front of the scrypt work), no password reset flow, and no email verification.
